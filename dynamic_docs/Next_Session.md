## This session's work, for context

Started as a pure design/mapping session, then PairedSurveyData was built once its design was agreed (see below) -- everything else stayed design-only, no other files in `code_base` changed. User supplied a table of 26 NHS-database chart types (Standard, Survey, Cross-service), each tied to a stored procedure name, and asked to work through which canonical data shape each belongs to before any visualisation/Base Chart discussion -- explicitly sequenced (data shapes first, charts later, survey rows last).

Checked `toolkit_nhs/transformers.py`'s `PROCEDURE_MAP` and `toolkit_indicators/transformers.py` first to establish the 10 already-supported rows from code, rather than assuming. User resolved the remaining 16 through conversation, one bucket at a time: multi-Metric-Series barcharts (still NumericSeries -- the shape already supports multiple named metrics per unit), a stacked-plus-benchmark variant (NumericCompositional, second Metric-Series is a local benchmark), a list-based stacked barchart (CategoricalCompositional, structurally identical to the existing yn_chart multi-question pattern), two timeseries SPs (TimeSeries -- flagged that this codebase's TimeSeries is fed only by the separate Indicators toolkit, not NHS toolkit SP dispatch, so the shape match was the user's call, not inferred from the name), scatter plot and opening hours (both NumericSeries), and four of five survey SPs (all NumericCompositional, list/Yes-No values becoming counts).

The fifth survey SP (Sunderland/Modified Barthel) didn't fit any existing shape -- per-unit patient-level start/end score pairs, with stats needing to pool every patient record across every unit, not average pre-computed per-unit stats. Checked patient-identifiability before treating it as a real field (TBN data-handling rules) -- confirmed "patient name" is just a positional label ("Patient 1"), no PII concern. Designed a new fifth canonical shape, PairedSurveyData, through the same question-first process as the other four: single vs multiple Metric-Series (always one), what the patient label actually is (plain distinguishing string), and how rich the stats block should be (count_with_data/count_null plus mean_start/mean_end only, no median/quartiles/min/max yet). User then asked for it to be built once agreed. Built and wired: shape module, `dispatch.py`'s three generic dispatch points, `unit_has_data`, `shapes/__init__.py` exports, and `cache_reader.py` read support (write needed no change -- generic `dataclasses.asdict` serialisation already handles it). Full design and build status captured in Current_State. No transformer, no Base Chart, and no Stat Tags (`reference_ids.py`) integration yet -- flagged as open in Current_State and above.

Also resolved, along the way: cross-service charts (3 of the 26) need no new shape, only a new per-unit `metadata: dict` on the shared `Unit` base class -- reasoned through why the existing peer-group mechanism (population-table columns) can't hold this, since service membership varies per fetch rather than being a standing attribute of a unit's identity. Two rounds of back-and-forth on scope/structure before landing on: shared base, all four shapes, fully open-ended dict, no predefined schema required.

While explaining the (still unresolved) radar `has_valid_unit_data=False` caveat, established that the flag is entirely inert in the current code -- set and cache-round-tripped everywhere, never read by anything. User reframed the real issue as Base Charts needing proper support for single-unit-only charts (radar's actual behaviour), and banked it as a separate future task rather than solving it this session.

User asked for the full final mapping twice -- once as a markdown table, once reformatted as tab-separated text for pasting into Excel. Both given verbatim; the tab-separated version is preserved in Current_State for reference.
