## Status: This session built Output Tables end to end -- a full second content-construction pathway alongside Charts, mirroring its architecture throughout (grid authoring, a Base Table library, Custom Tables, a Preview sandbox, Running Order integration). Ten Base Tables were built and iterated live. Two real cross-cutting bugs were found and fixed (a table/chart sizing clamp causing genuine image resolution loss; a Streamlit widget-mount timing issue causing a Sizing box to show a stale value). The PDF export image-quality question was investigated thoroughly and accepted as a known PowerPoint limitation for now. All four applicable governed documents updated in the mirror; re-upload prompted this close-down.

### What works (built this session)

- **Output Tables -- a new content-construction pathway, built from zero.** A table is now rendered the same way a chart is: a grid of content, composited into a single image by a Base Table function, inserted via its own Running Order function (`insert_table`). Mirrors the Charts/Base Charts architecture deliberately throughout. See Architecture Decisions 23-24, Functional Spec Section 11.2, Feature List's new "Output Tables" section.
  - **Grid model.** An Output Table's content is an (N+1) x (M+1) grid stored in its own spreadsheet shape (not a flat table) -- row 0/column 0 hold column widths, row heights (each independently expected to sum to ~100% of the table's own width/height, validated on an explicit Update, tolerance +/-0.5%, never auto-corrected), and the table's own id (corner cell, display only). Content cells hold constant text or a Stat Tag id (`[3]`); chart-component cells (`{n}`) are recognised by the grammar but deliberately parked, not resolved or rendered.
  - **Creation.** Either directly on the new Output Tables tab, or via a `[Table:name,Rows:X,Columns:Y]` yellow box at template processing -- same name on re-upload reuses the existing table's grid untouched; `Rows`/`Columns` only apply to a genuinely new name.
  - **Ten built-in Base Tables** (`plain_grid`, `table_ledger`, `table_zebra`, `table_editorial`, `table_terminal`, `table_cardtile`, `table_pill`, `table_freeform`, `table_brutalist`, `table_softui`), each a standalone artefact taking `table_inputs` (content, column_widths, row_heights, width, height, tweaks) and returning image bytes only -- no shape-type scoping, since every Base Table takes the same resolved grid. `table_cardtile` was iterated twice live (first pass, then a rounded-corner/shadow/header-alignment rework).
  - **Custom Tables**, mirroring Custom Charts exactly: download a self-contained bundle, paste back AI-edited code for static validation and live preview, save under a new `table_type_ref`. From that point indistinguishable from a built-in.
  - **The Output Tables tab.** One shared selection box (Running Order row / Output Table by name, "+ New Output Table" last, revealing inline creation controls) drives both modes below it. Edit Grid is content authoring (raw grid, resize, Update, Excel round-trip). Preview mirrors the Charts sheet's own mechanics (table type, tweaks, sizing, Save to Running Order, Custom Tables, Reset) -- including sandbox-state persistence across Save/reopen, the same pattern Decision 21 already established for Charts.
  - **`insert_table`** resolves `table_type_ref` built-in-then-custom via `custom_tables.resolve.get_table_callable`, the same pattern `insert_chart` uses for Custom Charts.
  - New shared helper: `core/shared/infrastructure/id_generation.py` (`to_base36`/`next_id`) -- Stat Tags' own id issuance was refactored onto this, so the two id spaces (`table_id`, Stat Tag `tag`) share encoding logic without sharing a counter.
- **Table and chart sizing bug fixed.** `insert_table`'s and `assembly_engine._render_chart_image`'s conversion from EMU to the percent-of-shorter-page-dimension value a Base Table/Base Chart's `width`/`height` parameters expect previously clamped the result to a 10-100 range. Any row whose real placed size exceeded the fixed 7.5in reference was rendered at the clamped, smaller size, then stretched to its true larger placement size on the slide -- a genuine, silent loss of resolution. Both clamps removed. See Architecture Decision 25 and the new "Validate only where designed" principle (Structural Design Principles) this fix prompted: validation/clamping is now explicitly an architectural decision, raised with the architect before adding, not layered in ad hoc.
- **A Streamlit widget-mount timing bug fixed in the Output Tables Preview sandbox.** Selecting a Running Order row while "Edit Grid" (the default mode) was showing wrote the correct sizing values to session state, but the Sizing box's own widget -- which doesn't exist until Preview is opened -- wasn't picking them up on its first mount, showing its own `min_value` (1.0) instead, despite the underlying value being correct throughout (confirmed via temporary debug instrumentation, since removed). Fixed by re-asserting the value at the exact moment Preview is entered, immediately before that widget's first mount for the viewing, rather than relying solely on the earlier, pre-mount write.
- **PDF export image quality investigated thoroughly; accepted as a known limitation for now.** `save_pdf` now uses `Presentation.SaveAs(path, 32)` (PowerPoint's "Save As PDF" pathway) rather than `ExportAsFixedFormat`, and `create_ppt` forces `autoCompressPictures="0"` on the presentation's own XML -- both genuine improvements, neither fully resolves the underlying issue. Embedded pictures in an exported PDF can still render below their true source resolution; this is understood, following real research, to be inherent to PowerPoint's own PDF-writing engine, not something further code changes or settings can currently fix -- confirmed not fixable by rendering DPI (tested up to 450, tables already render fine in the pptx itself), not fixable by any accessible PowerPoint setting or registry key, and every viable alternative pathway (LibreOffice, third-party PDF printer drivers, slide-image export + reassembly, Adobe Acrobat automation) was reviewed and rejected for its own reasons -- see Architecture Decision 26. May need PowerPoint reconsidered as the reporting middleware longer-term if this becomes a bigger issue; not something to action speculatively.

### Known gaps / not yet done (carried forward or new)

- **Chart-component cells (`{n}`, a saved chart embedded in a table cell) are recognised by the grid's own grammar but not resolved or rendered.** Deliberately parked from the very start of this session's design conversation -- genuinely new scope, not a bug.
- **A manually-created Output Table has no automatic route onto the Running Order.** Only a yellow-box-created one gets an `insert_table` row at template processing; a tab-created one needs the tab's own Save to Running Order (Insert above/below an existing row).
- **PDF image resolution remains below source quality for embedded pictures** -- accepted as a PowerPoint-inherent limitation this session, not something to keep chasing without a genuinely new angle. See Architecture Decision 26.
- **`chart_type_ref` -> `base_chart_name` rename -- still agreed in principle, still explicitly deferred.** Breaking change, needs a file version bump and its own dedicated session.
- **Custom Charts round-trip testing still limited to one chart type** (`ranked_column`) from a prior session.
- **Custom Tables round-trip testing not yet done at all** -- built and wired this session, but no chart type or a genuinely new Custom Table has been taken through the full download/edit/paste-back/save loop yet.

### Resolved this session

- Table/chart sizing clamp causing genuine rendered-resolution loss on any row exceeding the fixed 7.5in reference -- both ceiling and floor removed (Decision 25).
- Output Tables Preview sandbox showing a stale sizing value on first Preview-mode entry after selecting a Running Order row -- fixed by re-asserting the value at the moment Preview mounts, not only at row-selection time.
- `StreamlitDuplicateElementId` crash on Save to Running Order -- the Output Tables tab's button had identical label/params to the Charts sheet's own (Streamlit runs every tab's code every rerun regardless of which is visible) -- fixed with explicit keys; several other keyless buttons in the same tab given defensive keys too.
- `StreamlitAPIException` writing to `ot_ro_choice`/`ots_target_row_choice` after their own widgets had already rendered in the same run -- fixed via the same pending-key deferred-apply pattern already used elsewhere in this tab.
