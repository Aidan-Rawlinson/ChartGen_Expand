## Status: Major cross-cutting fix this session -- every Base Chart and Base Table now renders real `<text>` (not glyph outlines) via a "draw everything 5x bigger, place at real size" workaround for a PowerPoint SVG-compression bug that mis-spaced individual characters. Two separate, unrelated PDF/PowerPoint-COM reliability fixes also landed. Architecture and Feature List updated and re-uploaded; Glossary still carries the same stale Base Table count, deliberately left for next time.

### This session's work

**The core problem.** Real `<text>` in an embedded SVG (`svg.fonttype = "none"`) makes PowerPoint's own SVG-handling mis-space individual characters -- most visible on decimal-heavy labels ("0.000"). This is what Architecture's Decision 27 had previously (and, it turns out, wrongly) attributed to a searchability limitation and reverted from. Confirmed this session, via a real PPTX/PDF round-trip test, that it's actually a lossy-compression artefact PowerPoint applies to real text specifically -- and that it can be worked around.

**The fix, proven and now rolled out everywhere.** Every Base Chart/Base Table is called with `width_emu`/`height_emu` multiplied by a fixed factor (settled on `5`, after testing `10` and knowing about an earlier, fully-reverted `4x` exploratory pass from a prior session), draws itself at that inflated size, and is placed back on the slide/page at the real, unmultiplied target size -- `add_svg_picture` already scales an SVG's own content to whatever placement box it's given, so no resize-after-insert step is needed. A canvas being bigger does nothing on its own for a chart's *absolute* point-based sizes (fontsize, linewidth, markersize, fixed-inch padding), so every Base Chart/Base Table also carries its own local `TEXT_SCALE` constant (matching the system layer's `CHART_RENDER_SCALE` exactly, by convention -- not shared via import, per the standalone-artefact rule) multiplying every such literal. A chart/table that already computes its own sizes proportionally from its own canvas (the `line_ci_*` diagnostic-marker family) needed no `TEXT_SCALE` at all, only the `svg.fonttype` change.

**What actually got touched, in full:**
- `assembly_engine.py` / `insert_table.py` -- both carry `CHART_RENDER_SCALE = 5`; render calls inflated, placement calls unchanged (real size).
- All 23 Base Charts (20 original + the `line_ci_*` diagnostic-marker family, which turned out to be more numerous than expected) -- `svg.fonttype = "none"` everywhere; `TEXT_SCALE = 5` added and applied to every literal, except the self-scaling family.
- All four Base Tables -- `plain_grid`, `table_cardtile`, and two previously-undocumented ones discovered mid-session, `ci_grid`/`ci_cardtile` -- same treatment.
- `insert_table.py`'s chart-in-table-cell placement math -- a `chart_cells` rectangle now correctly divided by `CHART_RENDER_SCALE` at the placement boundary only (not the render boundary), since it comes back from an already-inflated table call. Same correction applied to the Output Tables tab's own Preview splice.
- `charts_tab.py` / `output_tables_tab.py` -- both preview render calls inflated, display size unchanged; Export Picture deliberately exports the oversized artefact (matching exactly what's embedded in a PPTX), not shrunk back down.
- `custom_charts/contract.py` / `custom_tables/contract.py` -- rewritten to tell an AI author the real mechanism (pre-inflated `width_emu`/`height_emu`, `svg.fonttype="none"` now required, `TEXT_SCALE` needed in their own code too). Both bundle-building call sites now pass the true inflated size.

**Two separate PDF/PowerPoint-COM reliability fixes, unrelated to the above, both in `save_pdf`/`save_ppt` (`assembly_engine.py`):**
1. `deck.Close()`/`powerpoint.Quit()` previously only ran on the success path -- any exception skipped both, leaving `POWERPNT.EXE` orphaned indefinitely. Fixed with nested `try`/`finally` guaranteeing each cleanup step regardless of what fails above it.
2. A separate, confirmed cause of lingering PowerPoint even on a fully successful run: `comtypes` holding a COM reference alive slightly longer than Python's own scope suggests. Fixed with explicit `del deck`/`del powerpoint` after `Quit()` -- a `gc.collect()` was tried first, confirmed to work, but added a real 10-30s delay (a full collection walks the entire live object graph, now bigger given the 5x rendering work above) and was removed once the plain `del`s were confirmed sufficient alone.
3. A third, separate issue -- `save_pdf` failing with a stuck modal-dialog error against a SharePoint/OneDrive-synced output path, PDF never produced, PPTX opened fine by hand afterwards (ruling out corruption) -- fixed with a new shared `_delete_existing_and_save` helper (used by both `save_ppt`/`save_pdf`): deletes any existing file first (confirming deletion completed), saves, then checks the file's size twice, 0.3s apart, before proceeding -- negligible in the normal case, enough to avoid handing COM a file mid-sync.
