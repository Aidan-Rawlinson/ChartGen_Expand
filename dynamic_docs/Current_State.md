> **Phase: Expansion.** The major refactor is complete. `code_base` and the six governed documents describe a stable, refactored base. This phase is about building new functionality on top of that base -- which means structure and logic in both the code and the documents SHOULD be expected to change, repeatedly, as each new feature lands. Do not treat the current structure as fixed or sacred. Do not read a structural mismatch between what's documented and what's proposed as an error to flag cautiously -- during this phase, it's the expected shape of the work. Ground truth discipline (Maintenance Guide Section 4) still applies fully: check actual code before updating docs, present-tense only. What changes is your posture going in -- expect churn, don't resist it.
>
> **Standing rule (confirmed by the user, still in force): Base Charts and Base Tables are never documented in the governed docs -- not their existence, not their internals.** Only a genuine core-system-level change belongs there. Do not log a new Base Chart/Table's existence "for completeness." This extends to memory and session notes too, not just governed docs -- a Base Chart's own implementation detail (internal assumptions, data-handling quirks) is never worth recording anywhere; it's outside the system boundary, the same way an Excel custom chart template's own internals are.
>
> **Standing rule: avoid unasked-for defensive coding.** Silent clamps, silent drops-on-mismatch, silent fallback defaults -- this session found and fixed two real bugs caused by exactly this pattern (a UI silently discarding a mismatched stored value instead of surfacing the mismatch; an Excel reader treating "no label" as "no value"). When a value might not resolve, let it fail visibly or flag it, rather than pre-emptively guarding against it without being asked.
>
> **Standing rule: a value the person actually picked or typed is never silently rewritten, reconstructed, or re-derived later** (on export, on re-save, etc.). If something needs deriving from live data, it happens once, at the point of actual use, not retroactively applied to what's already stored.

## Status: Radar-family transformers finished and correctly returning real per-unit data. Several long-standing Running Order/Excel round-trip bugs found and fixed this session, most significantly the period-field storage model, which was fundamentally rebuilt (not patched) partway through. `metric_periods` referencing a period this report doesn't have no longer halts the row -- it's now the Base Chart's own concern, same as any other "no data" case.

### This session's work

**Radar-family transformers finished.** `sp_a_generic_radar_chart` now reads real per-submission data straight out of its own response's `tableData` in a single call (`has_valid_unit_data=True`) -- confirmed against live JSON that this SP's structure differs from what was assumed (segments live in `yearData`, real per-unit rows already sit in `tableData`, one row is the network's own aggregate and is excluded). `sp_a_generic_radar_to_dual_bar` is a genuinely different SP under the same shape mapping -- `tableData` is always empty for it, so it needed the per-organisation `get_chart_data` cycling approach instead (`transform_radar_to_dual_bar`, `CYCLE_PROCS` in `transformers.py`, cycling helper in `fetch.py`). Known, unverified limitation carried forward: cycling is keyed on `organisation_id`, not `submission_id`, so an organisation with more than one submission gets identical values across them.

**Submission code normalisation.** New `toolkit_nhs/submission_codes.py` (`normalise_submission_code`) fixes a real data-quality issue in the API's own `submissionCode` field -- e.g. `"PH50 "` (trailing space, no leading zero) corrected to `"PH050"`. Applied everywhere a raw code becomes a ChartGen `unit_code`: all four transformers using `submissionCode`, plus `api_client.get_submissions` (so the population/submissions table matches).

**`outputAvailability` filtering removed entirely from the Indicators toolkit fetch.** `toolkit_indicators/transformers.py` no longer filters `availableDates` by whether a period's `outputAvailability` had passed as of the moment Fetch happened to run -- every period the API returns is now kept, in the API's own given order. This was a VBA-derived rule that didn't fit this system: period visibility depended on *when Fetch was run*, not on anything about the data itself, which meant a period could be permanently baked out of a cached shape depending on fetch timing, silently breaking any Running Order row referencing it later. `fetch.py`'s now-unused `project_dates` extraction was removed too, not left in place.

**CI "target-checking" TimeSeries Base Chart family finalised.** Deleted `line_ci_0_5pct`; renamed `line_ci_median`->`line_ci_at_least_median`, `line_ci_5pct`->`line_ci_at_most_5pct`, `line_ci_2`->`line_ci_at_most_2`; added `line_ci_at_most_median`, `line_ci_0`, `line_ci_at_least_90pct`, `line_ci_100pct`. `registry.py` and `chart_type_map.csv` both updated.

**Two real bugs found and fixed, unrelated to each other:**
- `chart_type_map.csv` (a static CSV, separate from `registry.py`) still listed the old CI chart names after the rename above -- silently broke the Charts sheet and the Running Order xlsx's own dropdown for any row using a current name, since `get_valid_chart_refs_for_cache_file` reads this file, not the registry.
- `batch_process.py`'s per-unit run-log summary discarded `row_id` when building the error message shown on the Outputs tab -- a failure was previously unattributable to a specific row. Fixed in `batch_process.py`; `results.py`'s `err_result` already carried `row_id` correctly, so no other file needed the same fix.

**Running Order period-field storage model rebuilt.** `start_period`/`end_period`/`metric_periods` now store exactly what was picked or typed (e.g. `"July 2025(1338)"`) as a single value each -- never rewritten, reconstructed, or re-derived at export or import time. Numeric extraction happens in exactly one place system-wide: `cut_resolution.prepare_chart_cut`, via new shared helpers in `shared/infrastructure/period_ids.py` (`extract_period_id`, `extract_metric_period_ids`, `build_period_display`, `extract_period_label`). This replaced an earlier design (this session) that derived the display label fresh from a live lookup on every export -- which silently reverted to a bare id the moment a report's own period range moved past that id, discarding a deliberate choice for a reason unconnected to the choice itself. The Charts sheet (`charts_tab.py`) now preserves a previously-stored value verbatim when the live shape can't resolve a label for an unchanged id, rather than rebuilding it label-less. Root fact established along the way: each Indicators report has its own independent period-numbering scheme -- the same calendar month can be a different `period_id` in two different reports. Not a bug; a fact about the source system.

**`metric_periods` referencing a period the report doesn't have no longer halts the row.** `shape_transforms.time_series_to_numeric_series` used to raise `ValueError` for an unresolvable period_id. It now produces a real output metric with every unit's value set to `None` -- the same "no data" state any other missing value already produces gracefully everywhere downstream. Removed the now-dead exception handling this created in `assembly_engine.py`, `charts_tab.py`, `text_tab.py`, `chart_store.py`, `insert_table.py`, and `stat_tags.py`.

**Architecture.md corrected.** A stale paragraph claiming `has_valid_unit_data` is `False` for the radar family was removed -- both radar transformers now set it `True` correctly, and it no longer needed banking as an open problem.
